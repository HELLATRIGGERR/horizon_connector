# Machine, link, and progression requirements

This is a requirements and evidence ledger, not a claim of complete parity. The reference is AE2 19.2.18 at [db17504a86128fdf3dae31f5fb7a112a646e0b93](https://github.com/AppliedEnergistics/Applied-Energistics-2/tree/db17504a86128fdf3dae31f5fb7a112a646e0b93), targeting Minecraft 1.21.1; Horizon targets 26.3. Source class paths below are relative to `src/main/java/appeng/` in that reference. The native `game/` paths below are under `ludovic111-horizon-7f8a668/crates/horizon-client/src/game/`. Assets, registration, recipe counts, and a helper's existence do not demonstrate gameplay.

**Implemented** means there is a corresponding native execution path. **Verified** names a specific test and its scope. **Open** means an identified omission or a requirement without adequate evidence. The baseline world evidence described in [STATUS.md](STATUS.md) belongs to the historical Stage 83 checkpoint; it does not verify later edits or every case listed here. The new world fixtures referenced below were prepared for a coordinated hidden-window run and their results must be recorded separately.

## Current verification

`scripts/test-armor-stand-formation-oracle.ts` compiles the unchanged Minecraft 1.21.1 `ArmorStandItem` from the pinned source jar against bounded host stubs. It passes downward-face refusal, block and entity collision refusal, item consumption, the six directional-context yaw values and a single successful spawn with its effects. This is a source oracle; the native normal-mode Armor Stand operation still requires an implemented, passing physical world run.

`core/settings/TickRates` and `api/networking/ticking/TickingRequest` accept source-configured signed integers without enforcing positive ordered bounds. Native `ae2_tick_config.rs` currently falls back to defaults for nonpositive or reversed ranges. This is a known setting-parity gap even though those source values are documented as unsupported; ordinary positive ordered values and signed midpoint overflow have dedicated native checks.

The new common gameplay settings additionally implement source bounds/defaults for `powerRatios.forgeEnergy`, `usageMultiplier`, `gridEnergyStoragePerNode`, `p2pTunnelEnergyTax`, and `p2pTunnelTransportTax`. `ForgeEnergyAdapter`, `EnergyService`, `PowerMultiplier`, and `FEP2PTunnelPart` are the reference for the conversion, node-event capacity update, configured usage, and separate energy/transport taxes. The server-thread `tests/world/common-config-power.ts` run passed physical FE injection, live changes, storage capacity, idle and channel-pathing consumption, unrelated-section retention and restart. The server-thread `tests/world/p2p-configured-tax.ts` run passed with a finite carrier and real FE and item transfers. The FE sink path commits fractional accepted AE before truncating its returned FE, matching `ForgeEnergyAdapter.receiveEnergy`; the server-thread `tests/world/fe-partial-acceptance.ts` run passed that physical boundary and restart. `scripts/test-stored-energy-oracle.ts` compiled the actual pinned Java `StoredEnergyAmount` with minimal type stubs and matched nine numeric cases bit-for-bit against `ae2-machines-core` (including simulation, the minimum amount, residual rounding, and maximum capacity). The private-block paths and saved energy-cell loading use those source operations; the server-thread `tests/world/stored-energy-boundary.ts` run passed real sub-minimum rejection, exact-boundary insertion, maximum cap and restart. Wider extreme-number rounding and tax paths remain open until exercised against the source.

`BlockItem.updateBlockStateFromTag` applies recognized valid item properties and ignores invalid ones. The Wave 15 `tests/world/block-item-state-components.ts` run passed real player placement of a hive with honey level four, an ignored invalid property and a resident bee, including restart. Formation component/door and normal player hive/energy regressions passed. Other callback-sensitive cases, including Formation golem/Wither spawning, remain open. The Wave 15 `tests/world/client-container-component-wire.ts` run passed real Horizon client receipt and creative-slot return of shulker lock and loot, hive bees and block state, colliding custom data, and restart. The compatibility envelope is Horizon-to-Horizon transport, not a vanilla protocol or Java mod interoperability claim. The Wave 16 extension carries the complete component patch retained by Horizon, including modeled nested items, transient map processing and removals, with a reader for the earlier envelope. It also retains unchanged source potion, book and enchantment payloads beside the fields Horizon models; editing those modeled fields invalidates the corresponding raw value. Focused wire tests passed, as did the server-thread `tests/world/client-complete-component-wire.ts` round trip through real creative inventory, restart and player placement, and `tests/world/cell-rich-item-components.ts` storage and retrieval of a potion, written book and enchanted sword through a physical cell and restart.
